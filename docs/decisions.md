# Прийняті рішення та відхилення від ТЗ

## Модель

- **Семантика `TwoPhase.tla` і `MCTwoPhase.tla` не змінювалась.** Обидва модулі взято
  дослівно з попереднього етапу. У `TwoPhase.tla` додано лише блок-коментар «КАРТА: дія
  TLA+ → подія в мікросервісах» і опис змінних. Через це номери рядків у логах TLC
  зміщені відносно старих логів; на вердикти це не впливає.
- Бага в моделі не знайдено: усі вердикти збіглися з еталоном, кількість станів у
  «правильних» конфігураціях — точно (1 840 / 28 832 / 477 760 / 163 / 28 828).

## Запуск TLC

- **Конфігурації з очікуваним порушенням запускаються з `-workers 1`**, решта — з
  `-workers auto` (як у ТЗ). Причина: з кількома воркерами TLC щоразу знаходив інший
  контрприклад (порядок обходу залежить від потоків). Для демонстрації і документації
  потрібна відтворювана траса: те, що студент покаже на парі, має збігатися з
  діаграмою в репозиторії. Ці перевірки тривають 0,6–4 с, тож на швидкість це не впливає.
- **Додано `-fp 1 -seed 1`.** Без них TLC випадково обирає поліном відбитків, і
  liveness-контрприклад (`NoTMRecovery_Termination`) усе одно відрізнявся між прогонами
  навіть з одним воркером. Із фіксованими значеннями всі три контрприклади стабільні.
- **Додано `-noGenerateSpecTE`.** Інакше TLC пише `*_TTrace_*.tla` поруч зі
  специфікацією. `-metadir` — у тимчасову папку (як у ТЗ).
- Еталонна кількість станів закладена в `scripts/common.py` і перевіряється в
  `run_all.py`: «збіг» для «правильної» конфігурації означає і правильний вердикт, і
  точну кількість станів.
- З логів прибирається рядок JVM `Picked up JAVA_TOOL_OPTIONS ...` — він залежить від
  машини (налаштування проксі) і до перевірки стосунку не має.

## Контрприклади

Фактичні траси трохи відрізняються від «типових» у ТЗ (ТЗ це допускає):

| Конфігурація | Типова в ТЗ | Отримана |
|---|---|---|
| NoTMRecovery_Deadlock | Prepare ×3 → TMCrash | така сама: `RMPrepare` payment, inventory, order → `TMCrash` |
| Mutant | ChooseToAbort(payment) → Prepare(inventory) → TMRcvPrepared → TMCommit → RcvCommit(inventory) | `RMPrepare(payment)` → `TMRcvPrepared(payment)` → `TMCommit` → `RMRcvCommit(payment)` → `RMChooseToAbort(inventory)` — суть та сама: один committed, інший aborted |
| NoTMRecovery_Termination | — | `RMChooseToAbort(payment)` → `RMPrepare(order)` → `RMPrepare(inventory)` → `TMCrash` → stuttering |

Нові версії TLC друкують аргументи дій (`RMPrepare("payment")`). Парсер у `common.py`
бере їх звідти, а для старих версій без аргументів відновлює аргумент за різницею
сусідніх станів.

## TLAPS

Етап виконано повністю, у межах таймбоксу: `tlapm` встановився з бінарного релізу,
доведення `spec/TwoPhaseProofs.tla` закрилося з першої спроби — **61 з 61
зобов'язань**, без `OMITTED`.

- Доведено: `Spec => [](Consistency /\ CommitValidity /\ FollowsTM)` для довільної
  скінченної множини `RM`, де `Spec == Init /\ [][Next]_vars`.
- Припущення `ASSUME NotMutant == Mutant = FALSE` вписано в модуль доведення (не в
  модель).
- Контроль: без `NotMutant` зобов'язання для `TMCommit` не доводиться (1/60 failed), тобто
  доведення не тривіальне.
- Liveness (L1–L4) у TLAPS не доводилась: це суттєво складніше (темпоральна логіка з
  fairness) і поза межами ТЗ. Liveness перевірено TLC для 2–4 сервісів.
- `tlapm` не завантажується за замовчуванням (≈50 МБ, лише Linux): `setup_tools.py --tlaps`.
  `run_all.py` запускає доведення, якщо `tlapm` встановлено, і пропускає з повідомленням,
  якщо ні. У CI доведення перевіряється.

## Діаграми

- Ручні діаграми рендеряться без Graphviz: у state/activity/component — `!pragma layout
  smetana`; sequence і mindmap PlantUML малює сам.
- Згенеровані з контрприкладів діаграми рендеряться в `diagrams/rendered/` з префіксом
  `generated_` (наприклад `generated_Mutant.png`), щоб не перетинатися з ручними версіями.
- Учасник «Мережа» на згенерованих діаграмах є: повідомлення йдуть через неї, бо в моделі
  відправка і отримання — різні кроки.

## Скрипти

- Додатково до ТЗ: `run_all.py --only tlaps`, `--timeout`; `run_one.py --list`, `--save`;
  `render_diagrams.py <фільтр>`; `setup_tools.py --tlaps`.
- Частковий прогін (`--only`, `--config`) не стирає результати інших перевірок: нові записи
  зливаються з наявним `summary.json`.
