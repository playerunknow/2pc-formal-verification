# Команди: що запускати, навіщо і що відбувається

Тут для кожної команди коротко розписано: **навіщо** її запускати, **що комп'ютер
робить** під капотом, **що з'явиться** на диску і на екрані, скільки це **триває**.

Усі команди запускаються з кореня репозиторію (папка `2pc-formal-verification/`).

## Загальна картина

```
setup_tools.py  ──>  tools/                      (один раз: завантажити інструменти)
                       │
run_all.py      ──>  results/  +  diagrams/generated/*.puml   (усі перевірки)
                       │
render_diagrams.py ─> diagrams/rendered/*.png, *.svg          (картинки з .puml)

run_one.py      ──>  лише екран (для демо на парі)
```

Звичайний порядок: **1 раз** `setup_tools.py` → `run_all.py` → `render_diagrams.py`.
На парі — лише `run_one.py`.

Усе важке робить Java-програма (TLC, Apalache, PlantUML). Python-скрипти — це
«диригент»: вони запускають Java з потрібними параметрами, читають її вивід і
перетворюють його на зрозумілі таблиці, пояснення та діаграми.

---

## 1. `python scripts/setup_tools.py`

**Навіщо:** завантажити інструменти. Без цього жодна інша команда не працює.
**Коли:** один раз на новому комп'ютері (потрібен інтернет). Повторний запуск нічого не
перезавантажує, якщо все вже є.
**Триває:** 1–3 хвилини (≈150 МБ), повторно — 2–3 секунди.

**Що робить комп'ютер:**

1. Запускає `java -version` і перевіряє, що Java є і вона 17+. Якщо ні — пише, як
   встановити, і зупиняється.
2. Завантажує з GitHub у папку `tools/`:
   - `tla2tools.jar` — **TLC**, перебирає всі стани моделі;
   - `apalache/` — **Apalache**, доводить індуктивний інваріант (архів розпаковується);
   - `plantuml.jar` — **PlantUML**, малює діаграми.
3. Запускає кожен інструмент з `--version` і друкує версії.

**Що з'явиться:** папка `tools/` (у git не потрапляє, вона в `.gitignore`).

**Варіанти:**

| Команда | Що змінюється |
|---|---|
| `python scripts/setup_tools.py --tlaps` | додатково завантажує **TLAPS** (`tools/tlapm/`, ≈50 МБ, лише Linux) — для доведення для будь-якої кількості сервісів |
| `python scripts/setup_tools.py --force` | видаляє й завантажує все заново (якщо файл пошкоджено) |

---

## 2. `python scripts/run_all.py`

**Навіщо:** головна команда. Проганяє **всі** перевірки моделі і записує результати.
**Коли:** після зміни моделі або щоб отримати свіжі результати. На парі наживо не
потрібна (результати вже закомічені в `results/`).
**Триває:** ≈2 хвилини (з них ≈50 с — `Full_4`).

**Що робить комп'ютер:**

1. **TLC, 8 разів** — по разу на кожен файл `spec/configs/*.cfg`. Кожен раз це окремий
   процес Java, приблизно такий:
   ```
   java -Xmx4g -cp tools/tla2tools.jar tlc2.TLC -workers auto -config configs/Full.cfg MCTwoPhase.tla
   ```
   TLC читає модель (`spec/TwoPhase.tla` + `spec/MCTwoPhase.tla`), бере з `.cfg` кількість
   сервісів і список властивостей, і обходить **усі** можливі стани (як пошук у ширину).
   Або доходить до кінця («No error»), або зупиняється на першому порушенні і друкує
   контрприклад — найкоротший шлях до помилки.
2. **Apalache, 16 разів** — для 3, 4, 5 сервісів перевіряє 5 речей про індуктивний
   інваріант (база, крок, три наслідки) + 1 раз на мутанті. Це теж Java, але інструмент не
   перебирає стани, а питає SMT-розв'язувач Z3: «чи існує стан, який ламає інваріант?».
3. **TLAPS, 1 раз** — лише якщо встановлено через `--tlaps`. Перевіряє доведення
   `spec/TwoPhaseProofs.tla`. Якщо TLAPS немає — пише «пропущено» і йде далі.
4. Для кожної перевірки Python читає вивід інструменту, витягує вердикт, кількість станів,
   час і **порівнює з очікуваним** (таблиця очікувань — у `scripts/common.py`). Наприклад,
   для `Mutant` очікується порушення `Consistency`: якщо TLC його знайшов — це ✔.
5. Для трьох конфігурацій з порушенням викликає `trace_to_puml.py` і робить з контрприкладу
   sequence-діаграму.

**Що з'явиться / оновиться:**

| Файл | Що там |
|---|---|
| `results/tlc/<Конфігурація>.txt` | повний вивід TLC (8 файлів) |
| `results/apalache/<перевірка>.txt` | повний вивід Apalache (16 файлів) |
| `results/tlaps/TwoPhaseProofs.txt` | вивід TLAPS |
| `results/summary.md` | таблиці «очікувано / отримано / збіг» — для людей |
| `results/summary.json` | те саме для програм |
| `diagrams/generated/*.puml` | 3 діаграми з контрприкладів (лише текст; картинки — командою 4) |

**На екрані:** рядок на кожну перевірку з часом, вердиктом і ✔/✘, у кінці — підсумок.
**Код виходу:** 0 — усе збіглося з очікуваним, 1 — щось ні (тоді див. рядок з ✘).

Тимчасові файли інструментів пишуться в системну тимчасову папку і видаляються самі —
репозиторій не засмічується.

**Варіанти:**

| Команда | Що запускається | Час |
|---|---|---|
| `python scripts/run_all.py --quick` | усе, крім довгої `Full_4` | ≈1 хв |
| `python scripts/run_all.py --only tlc` | лише 8 перевірок TLC | ≈1 хв |
| `python scripts/run_all.py --only apalache` | лише 16 перевірок Apalache | ≈50 с |
| `python scripts/run_all.py --only tlaps` | лише доведення TLAPS | ≈4 с |
| `python scripts/run_all.py --config Mutant` | одна перевірка за назвою | 1–50 с |

Частковий запуск оновлює лише свої рядки в `summary.md` / `summary.json`, решта
залишається з попереднього прогону.

## 3. `python scripts/run_one.py <Конфігурація>`

**Навіщо:** для **демонстрації наживо**. Запускає одну перевірку TLC і пояснює результат
людською мовою.
**Коли:** на парі, або щоб самому зрозуміти, що знайшов TLC.
**Триває:** 1–4 секунди (крім `Full_4` ≈50 с — її наживо не запускати).

**Що робить комп'ютер:** те саме, що `run_all.py` для однієї TLC-конфігурації (один процес
Java), але нічого не записує на диск. Замість цього друкує:

- великий вердикт: `NO ERROR` або `ПОРУШЕННЯ`;
- скільки різних станів перевірено;
- якщо є контрприклад — **кожен крок** з поясненням українською і станом усіх сервісів:
  ```
  крок 5   TMCrash      координатор впав
           payment=prepared inventory=prepared order=prepared | TM=init (впав)
  ```
- чи це очікуваний результат (✔).

**Три команди для демо:**

| Команда | Що покаже | Навіщо показувати |
|---|---|---|
| `python scripts/run_one.py Full` | `NO ERROR`, 28 832 стани | повна модель зі збоями — усе виконується |
| `python scripts/run_one.py NoTMRecovery_Deadlock` | `ПОРУШЕННЯ`: усі «так», координатор упав, далі — нічого | 2PC блокується без відновлення координатора |
| `python scripts/run_one.py Mutant` | `ПОРУШЕННЯ Consistency`: payment закомітив, inventory відкотив | властивості справді ловлять зламаний протокол |

Контрприклади завжди однакові (TLC запускається в детермінованому режимі), тож на парі
буде те саме, що в документації.

**Варіанти:**

| Команда | Що робить |
|---|---|
| `python scripts/run_one.py --list` | список усіх 8 конфігурацій і що від кожної очікується |
| `python scripts/run_one.py Mutant --save` | те саме + записує лог у `results/tlc/` і діаграму в `diagrams/generated/` |

---

## 4. `python scripts/render_diagrams.py`

**Навіщо:** перетворити текстові діаграми `.puml` на картинки.
**Коли:** після зміни будь-якого `.puml` або після `run_all.py` (бо він оновлює
`diagrams/generated/`).
**Триває:** ≈1 хвилина (15 діаграм × 2 формати).

**Що робить комп'ютер:** для кожного файлу `diagrams/*.puml` і `diagrams/generated/*.puml`
двічі запускає PlantUML (`java -jar tools/plantuml.jar -tpng ...` і `-tsvg ...`). PlantUML
читає текстовий опис діаграми і малює її. Graphviz не потрібен.

**Що з'явиться:** `diagrams/rendered/<назва>.png` і `.svg`. Діаграми з контрприкладів
отримують префікс `generated_` (наприклад `generated_Mutant.png`).

**Варіант:** `python scripts/render_diagrams.py Mutant` — лише діаграми, у назві яких є
«Mutant».

Якщо в `.puml` помилка — скрипт покаже, у якому файлі, і текст помилки PlantUML.

---

## 5. `python scripts/trace_to_puml.py <лог TLC>`

**Навіщо:** окремо перетворити контрприклад TLC на діаграму. Зазвичай вручну **не
потрібна**: `run_all.py` викликає її сам.

```bash
python scripts/trace_to_puml.py results/tlc/Mutant.txt -o diagrams/generated/Mutant.puml
```

**Що робить комп'ютер:** лише Python, без Java. Читає лог, знаходить кроки `State 1`,
`State 2`, …, для кожного кроку бере назву дії (`RMPrepare("payment")`, `TMCrash`, …) і
значення змінних, і пише `.puml`: стрілка на кожне повідомлення, червона нотатка на
кожне падіння, у кінці — підсумковий стан і назва порушеної властивості.

## Make (необов'язково)

Якщо є `make` (Linux/macOS), ті самі команди коротше:

| Make | Що запускає |
|---|---|
| `make setup` | `setup_tools.py` |
| `make setup-tlaps` | `setup_tools.py --tlaps` |
| `make verify` | `run_all.py` |
| `make quick` | `run_all.py --quick` |
| `make demo` | три демо-запуски `run_one.py` підряд |
| `make diagrams` | `render_diagrams.py` |

## CI на GitHub

Після кожного `git push` GitHub сам (файл `.github/workflows/verify.yml`) на чистій
машині: ставить Java і Python → `setup_tools.py --tlaps` → `run_all.py --quick` →
`render_diagrams.py` і прикладає папку `results/` як архів до запуску. Зелена галочка
біля коміту = усі вердикти збіглися з очікуваними. Нічого в репозиторій CI не комітить.

## Якщо щось не так

| Повідомлення | Що робити |
|---|---|
| `Java не знайдено` / `потрібна 17+` | встановити Java 21 (Ubuntu: `sudo apt install openjdk-21-jre-headless`, Windows: Temurin з adoptium.net) |
| `tools/tla2tools.jar не знайдено` | спершу `python scripts/setup_tools.py` |
| `не вдалося завантажити інструмент` | немає інтернету або заважає проксі |
| у `run_all.py` рядок з `✘ НЕ ЗБІГЛОСЯ` | відкрити відповідний лог у `results/` — там повний вивід інструменту |
| незрозумілі символи замість українських літер (Windows) | `chcp 65001` або Windows Terminal |
