# TLA+ для Python-розробника: шпаргалка

TLA+ — не мова програмування, а мова **опису поведінки**. Специфікація каже: які бувають
стани, з якого стану почати і які переходи між станами дозволені. Далі інструмент (TLC)
сам перебирає **всі** можливі поведінки і перевіряє, що в жодній із них не стається
нічого поганого.

Найближча аналогія: ви пишете не функцію, а **гру** (стан + правила ходів), а TLC грає в
неї всіма можливими способами одночасно.

## Оператори

| TLA+ | Що означає | Python |
|---|---|---|
| `/\` | і | `and` |
| `\/` | або | `or` |
| `~` | не | `not` |
| `=>` | якщо … то … | `(not a) or b` |
| `=` / `#` | дорівнює / не дорівнює | `==` / `!=` |
| `x \in S` | належить множині | `x in S` |
| `S \cup T`, `S \ T` | об'єднання, різниця | `S \| T`, `S - T` |
| `SUBSET S` | множина всіх підмножин | `powerset(S)` |
| `\A x \in S : P(x)` | для всіх | `all(P(x) for x in S)` |
| `\E x \in S : P(x)` | існує | `any(P(x) for x in S)` |
| `[r \in RM \|-> "working"]` | функція (словник) | `{r: "working" for r in RM}` |
| `rmState[r]` | значення функції | `rm_state[r]` |
| `[rmState EXCEPT ![r] = "prepared"]` | копія з одним зміненим ключем | `{**rm_state, r: "prepared"}` |
| `[type \|-> "Commit", rm \|-> "-"]` | запис (record) | `{"type": "Commit", "rm": "-"}` |
| `[RM -> BOOLEAN]` | множина всіх функцій RM → bool | «тип» `dict[str, bool]` |
| `IF c THEN a ELSE b` | умова | `a if c else b` |
| `LET m == ... IN ...` | локальне позначення | `m = ...; return ...` |
| `Op == ...` | визначення | `def op(): return ...` |

## Кроки: штрих, UNCHANGED

```tla
RMPrepare(r) ==
    /\ rmUp[r]                                       \* умова: сервіс працює
    /\ rmState[r] = "working"                        \* умова: ще не голосував
    /\ rmState' = [rmState EXCEPT ![r] = "prepared"] \* новий стан
    /\ msgs' = msgs \cup {PreparedMsg(r)}            \* нове повідомлення
    /\ UNCHANGED <<tmState, tmPrepared, tmUp, rmUp>>
```

`x'` (зі штрихом) — значення змінної **на наступному кроці**. Дія — це логічна формула
про пару станів «до» і «після». Рядки без штриха — це умови (guard), рядки зі штрихом —
присвоєння. `UNCHANGED <<a, b>>` означає `a' = a /\ b' = b`.

Як те саме виглядало б у Python:

```python
def rm_prepare(s: State, r: str) -> State | None:
    if not (s.rm_up[r] and s.rm_state[r] == "working"):
        return None                      # дія зараз неможлива
    return replace(
        s,
        rm_state={**s.rm_state, r: "prepared"},
        msgs=s.msgs | {("Prepared", r)},
    )                                    # решта полів без змін
```

`Next` — це «або» всіх дій: на кожному кроці відбувається будь-яка одна з можливих дій.
Вибір **недетермінований**: TLC перебирає їх усі.

## ENABLED

`ENABLED A` — «дію A зараз можна виконати». У Python: `rm_prepare(s, r) is not None`.
Саме так перевіряється відсутність Deadlock: `~AllDone => ENABLED ProtocolStep`.

## Темпоральні оператори

Вони кажуть не про один стан, а про **всю поведінку** (нескінченну послідовність станів).

| TLA+ | Читається | Значення |
|---|---|---|
| `[]P` | «завжди P» | P істинне в кожному стані поведінки |
| `<>P` | «колись P» | P стане істинним хоча б в одному стані |
| `[]<>P` | «знову і знову P» | P стає істинним нескінченно часто |
| `P ~> Q` | «P призводить до Q» | щоразу після P колись настане Q (`[](P => <>Q)`) |
| `[][A]_vars` | «кожен крок — це A або нічого не змінилося» | обмеження на всі кроки |

Аналогія з тестами: `[]P` — це `assert P` після кожного кроку; `<>P` — «тест не
закінчиться, поки P не стане істинним». Перевірити `<>P` звичайним тестом неможливо:
скільки б ви не чекали, «ще не настало» не означає «ніколи не настане». TLC може, бо
шукає в графі станів **цикли**, де P так і не настає.

## WF і SF (справедливість)

Без додаткових умов TLA+ дозволяє поведінку, у якій система просто «завмирає» і більше не
робить кроків. Тоді жодне `<>P` не виконується. Справедливість забороняє такі поведінки:

- `WF_vars(A)` (weak fairness): якщо A **постійно** можлива, вона колись станеться.
  Аналогія: справедливий планувальник потоків не голодує потік, який весь час готовий.
- `SF_vars(A)` (strong fairness): якщо A можлива **нескінченно часто** (з перервами), вона
  колись станеться.

## Що робить TLC: це BFS

TLC — це, по суті, пошук у ширину по графу станів:

```python
from collections import deque

def tlc(init_states, next_states, invariant):
    seen = set(init_states)
    queue = deque((s, [s]) for s in init_states)
    while queue:
        state, trace = queue.popleft()
        if not invariant(state):
            return trace                     # контрприклад: найкоротший шлях
        for nxt in next_states(state):       # усі дії Next, усі аргументи
            if nxt not in seen:
                seen.add(nxt)
                queue.append((nxt, trace + [nxt]))
    return None                              # "No error has been found"
```

- «distinct states» у звіті TLC — це `len(seen)`: скільки різних станів існує;
- «depth» — найдовший із найкоротших шляхів від початку (рівень BFS);
- контрприклад завжди **найкоротший**, бо пошук у ширину.

Для liveness (`<>`, `~>`) TLC додатково шукає в побудованому графі цикли, на яких
обіцяне так і не настає, з урахуванням fairness.

Звідси й обмеження: кількість станів росте експоненційно з кількістю сервісів (2 сервіси —
1 840 станів, 3 — 28 832, 4 — 477 760). Тому TLC перевіряє маленькі конфігурації.

## Індуктивний інваріант

Як довести, що властивість P виконується в **усіх** досяжних станах, не перебираючи їх?
Як у математичній індукції:

1. **База:** P істинна в початковому стані.
2. **Крок:** якщо P істинна в **якомусь** стані (будь-якому, не обов'язково досяжному),
   то після будь-якого кроку вона залишається істинною.

Проблема: `Consistency` сама по собі не індуктивна. Є недосяжні стани, де вона істинна, а
один крок її ламає. Тому формулюють сильнішу `IndInv`, яка «відсікає» такі стани, і
доводять, що `IndInv` індуктивна і з неї випливає `Consistency`.

Apalache перевіряє крок індукції символьно: замість перебору станів він передає SMT-
розв'язувачу Z3 питання «чи існує стан, де `IndInv` істинна, а після кроку — ні?». Відповідь
«ні» (`NoError`) — це доказ для виконань будь-якої довжини.

## Модулі, константи, конфігурації

- `EXTENDS TwoPhase` — як `from two_phase import *`.
- `CONSTANTS RM, Mutant` — параметри моделі. Їх значення задає `.cfg`-файл для TLC або
  оператор `ConstInit` для Apalache.
- `.cfg`-файл — «конфіг запуску»: які константи, яка специфікація, які інваріанти і
  властивості перевіряти.
